Publish your new website on GitHub

This guide is written for your existing repository, Chen-Muyang/Chen-Muyang.github.io, whose publishing branch is master. Your website address remains chen-muyang.github.io.

This guide explains the first publication and how deployment works. If the Fuwari site is already live, use the maintenance section for everyday changes. GitHub will build the site for you; you do not need Node.js on your computer to use this publishing method.

1. Understand the two downloads

  • Chen-Muyang-Fuwari-source.zip contains the editable website. This is the download to copy into your repository. After extracting it, open the Chen-Muyang-Fuwari-source folder.
  • Chen-Muyang-Fuwari-preview.zip contains an already compiled snapshot. It is useful for viewing the design locally. Do not copy this ZIP into the repository or use it instead of the source package.

The source package includes src, public, .github, package.json, and the build configuration. It contains no Git credentials, Git history, installed dependencies, or build cache. The old Jekyll folders already in your repository can stay there as reference; the new build uses src/content and public.

2. Install GitHub Desktop and sign in

  1. Download GitHub Desktop and install it.
  2. Open it and sign in to the GitHub account that owns Chen-Muyang/Chen-Muyang.github.io.
  3. Finish the browser sign-in prompts, then return to GitHub Desktop.

A repository is the website's project folder. A commit saves a version of your changes. Push uploads those commits. A branch lets you prepare the redesign separately. A pull request gives you a page to review and merge that branch.

3. Download your existing repository into Desktop

  1. Choose File → Clone repository.
  2. Select the URL tab and paste https://github.com/Chen-Muyang/Chen-Muyang.github.io.
  3. Choose a local folder you can find again, such as Documents/GitHub/Chen-Muyang.github.io.
  4. Click Clone and wait for it to finish.
  5. At the top, confirm that Current repository is Chen-Muyang.github.io and Current branch is master.
  6. Click Fetch origin. If it changes to Pull origin, click that too so you start from the latest version.

If this repository is already in Desktop, select it and fetch/pull instead of cloning a second copy. Finish or save any existing uncommitted work before copying the redesign. GitHub's cloning instructions.

4. Create a branch for the redesign

  1. Click Current branch → New branch.
  2. Name it fuwari-redesign and base it on master.
  3. Click Create branch.

The branch name at the top should now read fuwari-redesign. Uploading this branch alone will not deploy the new website. GitHub's branch instructions.

5. Copy the source files into the repository

  1. Right-click Chen-Muyang-Fuwari-source.zip in File Explorer and choose Extract All.
  2. Open the extracted folder until you can see package.json, src, and public together.
  3. In GitHub Desktop, choose Repository → Show in Explorer to open the cloned repository.
  4. Copy the contents of the extracted source folder into the cloned repository folder. Do not copy the outer Chen-Muyang-Fuwari-source folder itself.
  5. If Windows asks about files with the same names, choose Replace the files in the destination. Merge matching folders.
  6. Keep the existing .git folder and old Jekyll folders. There is no .git folder in the ZIP, so you are not replacing your repository history.

Check the result before continuing. These files must be at these locations relative to the cloned repository:

Chen-Muyang.github.io/
  .github/workflows/pages.yml
  package.json
  pnpm-lock.yaml
  astro.config.mjs
  src/config.ts
  src/content/posts/
  src/content/notes/
  src/content/publications/
  public/files/Defense.pdf

If instead you see Chen-Muyang.github.io/Chen-Muyang-Fuwari-source/package.json, the files are one folder too deep. Move the extracted folder's contents up to the repository root. Enable View → Show → Hidden items in Explorer if you cannot see .github. Do not upload the ZIP file itself.

6. Save and upload the branch

  1. Return to Desktop. The Changes tab should show many new files and a few modified files.
  2. Confirm the files above are included. node_modules, dist, and .astro should not be listed.
  3. In the Summary box at the lower left, enter Upgrade website to Fuwari and fix publication PDFs.
  4. Click Commit to fuwari-redesign.
  5. Click Publish branch at the top. If the branch was already published, the button will say Push origin.

Committing is a local save; publishing/pushing sends it to GitHub. GitHub's commit instructions.

7. Open a pull request and let GitHub check the build

  1. In Desktop, choose Preview Pull Request or Create Pull Request. You can also visit your repository, select fuwari-redesign, and use Compare & pull request.
  2. Confirm base: master and compare: fuwari-redesign.
  3. Give it the title Upgrade website to Fuwari and click Create pull request.
  4. Wait for Build and deploy Fuwari / build to finish successfully. You can inspect it from the repository's Actions tab.

On a pull request, the workflow builds and checks the site but skips deployment. A green check means GitHub successfully installed dependencies, checked the source, built the search index, and verified the preserved routes and files. If it fails, open the failing run and its red step; fix that error before merging. GitHub's pull-request instructions.

8. Tell GitHub Pages to use the new workflow

  1. Open repository Settings → Pages. Before changing it, note the current Source, branch, and folder so you can restore them if needed.
  2. Under Build and deployment, set Source to GitHub Actions.
  3. The package already contains the required workflow at .github/workflows/pages.yml. You do not need to select or create another suggested workflow.

The old site used Jekyll. This redesign uses Astro, so this setting change is essential. Keep the repository name Chen-Muyang.github.io; the configuration is prepared for that root website address. GitHub's publishing-source instructions.

9. Merge and publish

  1. Return to the pull request. After its build succeeds, click Merge pull request, then Confirm merge.
  2. Open Actions → Build and deploy Fuwari and select the new run for master.
  3. Wait for both build and deploy to be green. The deploy job provides the live website link.
  4. Visit your website. If you still see the old design, press Ctrl + F5 or open a private browser window.
  5. Verify Publications shows the thesis with Paper (PDF) and Slides (PDF). Also open Notes, Blog Posts, and CV.

Back in Desktop, switch to master, click Fetch origin, and then Pull origin. Your computer now has the published version. Later edits pushed to master will automatically run this workflow again.

Troubleshooting

What you see What to check
There is no Fuwari workflow in Actions Confirm .github/workflows/pages.yml was copied and committed. Check the branch in GitHub.
Only the old Jekyll workflow runs Set Pages Source to GitHub Actions, and ensure the redesign has reached master.
Pull request is green but the live site is unchanged A pull request does not deploy. Merge it into master, then wait for the deploy job.
package.json or lockfile is missing The extracted package may be nested one folder too deep. Compare with the folder tree in Step 5.
Deployment says Pages is not configured Check Step 8 and your permission to administer this repository.
Actions are disabled by an organization policy Ask the repository/organization administrator to allow this workflow. Do not remove policy protections.
A photo or PDF returns 404 File names are case-sensitive online. Match public/files/Example.pdf with /files/Example.pdf.
A check fails after editing Markdown Check the lines between the opening and closing ---; dates and indentation matter. The error log names the file.

The provided workflow targets master. If you intentionally rename that branch, also update the branch names and deploy condition in .github/workflows/pages.yml.

If you want to undo publication

Before merging, you can simply leave the pull request unmerged. After merging, GitHub's pull-request page can offer Revert to create a new pull request that reverses the merge. Review and merge that reversal. Returning fully to the former Jekyll site also requires restoring Pages Source, branch, and folder to the settings you recorded in Step 8. Keep the old content folders until you are comfortable with the migration.

For everyday changes after publishing, read UPDATE-YOUR-WEBSITE.md. For the photo replacement map, read CUSTOMIZE.md.

A. Your normal update routine

  1. Open GitHub Desktop and select Chen-Muyang.github.io.
  2. Switch to master, then Fetch origin → Pull origin if a pull is offered.
  3. Choose Repository → Show in Explorer. Open the relevant file in a text editor, such as Visual Studio Code.
  4. Make your edits and save the files. On Windows, show file extensions so my-post.md does not accidentally become my-post.md.txt.
  5. Return to Desktop and review Changes. Enter a short summary, such as Add a note on spin fluctuations.
  6. Click Commit to master, then Push origin. Saving or committing alone does not update the live site.
  7. Open the repository's Actions tab. Wait for the Build and deploy Fuwari run to succeed, then refresh your website.

If your repository requires pull requests, or you want to check a larger change first, create a branch from master, commit/publish it, open a pull request, and merge after its build passes. The first-publication guide explains that process.

For a small text correction, you can also open the file on GitHub, click its pencil icon, edit, and use Commit changes. Then pull the new version in Desktop before your next local edit. Use Desktop for adding photos, PDFs, or several related files together.

B. Add a blog post

Create src/content/posts/my-new-post.md. Copy this example, changing the title, date, and body:

---
title: "A new research semester"
published: 2026-10-19
description: "A few thoughts about research and life at Penn State."
image: "/images/my-new-photo.jpg"
tags: [Physics, Life]
category: Life
draft: false
lang: en
---

Write your introduction here.

## A section heading

You can use **bold text**, *italics*, and [a link](https://www.psu.edu/).

![Describe what is in the photograph](/images/my-new-photo.jpg)

Inline mathematics works: $E = mc^2$.

$$
H = \sum_i h_i
$$

Put the corresponding photograph in public/images/my-new-photo.jpg. If you do not want a cover, use image: "" and remove the example photograph from the body. Images are optional: the template does not require a new background for each article.

The page normally appears at /posts/my-new-post/. published controls sorting; it is not a publication scheduler. A future-dated entry with draft: false will still be visible. Set draft: true while writing, then change it to false when ready. Drafts appear in the development server but are excluded from the production build, archive, and feed.

The four migrated posts have explicit slug: values preserving their former URLs. Keep those slugs unchanged when editing their contents. New posts do not need a slug, unless you want a custom path such as 2026/10/my-new-post (without leading or trailing /).

Optional front matter: updated: 2026-10-20 records a later edit. Quote titles containing punctuation such as a colon. Keep both --- lines, use spaces instead of tabs, and write dates in YYYY-MM-DD form.

C. Add a note or seminar

  1. Copy your PDF to public/files/Spin-Fluctuations.pdf.
  2. Create src/content/notes/spin-fluctuations.md with the following structure.
  3. Change the example details and write your explanation below the second ---.
---
title: "Spin fluctuation notes"
published: 2026-10-19
permalink: /teaching/spin-fluctuations
topic: Superconductivity
venue: Penn State University, Department of Physics
description: "Working notes on spin fluctuations and pairing."
paper: /files/Spin-Fluctuations.pdf
paperLabel: Read note (PDF)
---

A short introduction, assumptions, and references can go here.

The note appears automatically in Notes. The old /teaching/ URL is intentionally retained for this section. Use a unique permalink beginning with /teaching/, with no trailing slash. paperLabel can also be Slides (PDF) for a seminar deck. Notes do not currently support draft flags; add them to your published branch when ready.

D. Add a publication with both paper and slides

  1. Copy the PDFs into public/files/, for example My-Paper.pdf and My-Talk.pdf.
  2. Create src/content/publications/my-paper.md:
---
title: "Title of my paper"
published: 2026-10-19
permalink: /publication/my-paper
topic: Research paper
venue: "Journal or conference name"
description: "One or two sentences describing the work."
paper: /files/My-Paper.pdf
paperLabel: Paper (PDF)
slides: /files/My-Talk.pdf
---

Authors, an abstract, citation, and a DOI link can go here.

Every entry appears in Publications automatically; you do not need to register its topic in a separate configuration file. paper is required and slides is optional. If there are no slides, omit that entire line rather than leaving a blank value. You can optionally add presentation: /files/My-Talk.pptx for the editable PowerPoint download.

Your existing thesis already has working buttons for UndergraduateThesis.pdf and Defense.pdf. The slides PDF was exported from your existing Defense.pptx. Updating the PowerPoint alone does not refresh its PDF: in PowerPoint, use File → Export → Create PDF/XPS, save a new Defense.pdf, and replace public/files/Defense.pdf too. Keeping the same filename keeps existing links working. Publications do not currently support draft flags.

Use a wide landscape image for the banner (about 1920–2400 pixels wide) and a square image for the avatar (512 × 512 pixels or larger). The banner crops to fit the screen, so keep your subject near the center. The banner and avatar are optimized during the build. Post photographs are served from public as supplied; resize/compress very large new photos before adding them.

Replacing a file with the same name is the easiest method. Keep the actual file format correct: renaming a PNG to .jpg does not convert it. The current post photos are also used inside posts, so replacing one changes both uses. For an independent cover, add another image and change only the post's image: field.

To use a different banner filename, edit src/config.ts:

banner: {
  enable: true,
  src: "assets/images/my-banner.webp",
  position: "center",
  credit: { enable: false, text: "", url: "" },
},

Place that file at src/assets/images/my-banner.webp. Set enable: false to remove the background entirely. Set position to top, center, or bottom to adjust the crop. The avatar path is profileConfig.avatar in the same file.

F. Update your personal details and appearance

In src/config.ts, edit profileConfig.name, bio, and links. Edit siteConfig.title and subtitle for the site's name and description. Keep the quotation marks and commas around these values.

The default accent is themeColor: { hue: 165, fixed: false }. Change the hue (0–360) for a different default color. Visitors can adjust it themselves because fixed is false; setting it true hides the color picker. The light/dark control is already included. A visitor's saved preference may override the default you just changed, so test defaults in a private window.

For the homepage introduction, edit the visible text in src/components/HomeIntro.astro while leaving the HTML tags intact. For the About page, weekly poem, and CV, edit the Markdown files in the table at the top. The inherited CV is brief; expand it with your own verified details whenever you wish.

G. Optional local preview before uploading

You can publish using GitHub's build without installing these tools. For editing with a local preview:

  1. Install Node.js 24 from nodejs.org.
  2. In File Explorer, open the source/repository folder containing package.json. Type cmd in Explorer's address bar and press Enter to open a command window there.
  3. Run these commands one line at a time:
npm install --global pnpm@11.25.0
pnpm install --frozen-lockfile
pnpm dev

Open the local address printed by the server (normally http://localhost:4321). Changes refresh as you save. Press Ctrl + C to stop the server. To check the actual production build, including search:

pnpm check
pnpm build
pnpm verify
pnpm preview

Search uses the production index, so test it with pnpm preview, not pnpm dev. The compiled-preview ZIP also includes a standalone Node server and its own instructions; it needs no dependency installation.

H. Before each update

  • Check exact spelling and uppercase/lowercase in every new file path.
  • Open any new PDF and confirm that it is the intended document.
  • Keep migrated slugs and permalinks to preserve existing links.
  • Do not edit dist/ or node_modules/; they are generated, and changes there will be lost.
  • Commit the source and any new assets, then push and wait for the workflow to finish.

The verification script protects the migrated routes and the original four document filenames. If you intentionally remove those pages or rename those four files, you must also update scripts/verify-site.mjs; otherwise the build will correctly report that a preserved resource is missing. Adding new content or changing existing titles/text does not require changing that script.
